# 踩坑记录

> 每条记录按"现象 → 原因 → 解法"结构组织。

## 一、反序列化

### 1.1 LocalDateTime 反序列化失败（所有 CDC 记录解析失败）

**现象：** DWD 作业启动后，Iceberg 0 条数据，Kafka 消费组 LAG=0，看似正常但无输出。

**原因：** PostgreSQL CDC 输出的时间格式为 `2026-10-28 22:13:39.807295`（空格分隔），而 Jackson 默认 `JavaTimeModule` 期望 ISO-8601 格式 `2026-10-28T22:13:39.807295`（`T` 分隔）。格式不匹配导致所有 `CdcEnvelope` 反序列化失败，全部进入 DLQ。

**解法：** 自定义 `LocalDateTime` 反序列化器，同时接受空格和 `T` 分隔符。在 `JsonUtils.java` 中注册 `FlexibleLocalDateTimeDeserializer`。

```java
// 核心逻辑：用正则把空格替换为 T，再交给标准 LocalDateTime 解析
public LocalDateTime deserialize(JsonParser p, DeserializationContext ctxt) {
    String text = p.getText().trim();
    if (text.indexOf(' ') == 10) {  // yyyy-MM-dd HH:mm:ss
        text = text.replaceFirst(" ", "T");
    }
    return LocalDateTime.parse(text, DateTimeFormatter.ISO_LOCAL_DATE_TIME);
}
```

**教训：** CDC 源的时间格式与 Jackson 默认格式可能不一致，必须先看实际消息格式再写反序列化器。

---

### 1.2 Jackson 版本冲突：NoSuchFieldError

**现象：** 启动时报 `NoSuchFieldError: READ_DATE_TIMESTAMPS_AS_NANOSECONDS`。

**原因：** 不同依赖传递引入了不同版本的 Jackson，`jackson-databind` 和 `jackson-annotations` 版本不匹配。

**解法：** 在父 pom 中统一锁定 Jackson 版本（2.18.2），所有子模块继承。

```xml
<jackson.version>2.18.2</jackson.version>
<!-- dependencyManagement 中锁定 -->
```

## 二、Iceberg 写入

### 2.1 Kryo 序列化失败：NullPointerException（Iceberg committer 卡住）

**现象：** 数据能通过 JOIN，但 Iceberg committer 在 Checkpoint 时反复失败，无数据写入。

**报错：**
```
com.esotericsoftware.kryo.KryoException: NullPointerException:
Cannot invoke "java.util.Map.put(Object, Object)" because "this.wrapped" is null
Serialization trace:
  lowerBounds (org.apache.iceberg.GenericDataFile)
  dataFiles (org.apache.iceberg.io.WriteResult)
  writeResult (org.apache.iceberg.flink.sink.FlinkWriteResult)
```

**原因：** Iceberg 的 `GenericDataFile.lowerBounds` 是 `Map<Integer, ByteBuffer>`，常用 `Collections.emptyMap()` 等不可变 Map。Kryo 默认 Map 序列化器调用 `.put()` 时抛出 NPE。

**解法：** 自定义 `FlinkWriteResultKryoSerializer`，外层处理 `checkpointId`，内部 `WriteResult` 委托给 Iceberg 官方 `WriteResultSerializer`。然后在 `StreamEnvBase` 中注册。

```java
// Flink 2.2 注册方式（SerializerConfig 从 ExecutionConfig 移到了 SerializerConfigImpl）
((SerializerConfigImpl) env.getConfig().getSerializerConfig())
    .registerTypeWithKryoSerializer(FlinkWriteResult.class, FlinkWriteResultKryoSerializer.class);
```

**教训：** 复杂对象（含不可变集合、ByteBuffer 等）不能依赖 Kryo 默认序列化器，需自定义或复用官方序列化器。

---

### 2.2 Flink 2.2 注册 Kryo 序列化器的 API 变更

**现象：** 按旧版 Flink 写法 `env.getConfig().registerTypeWithKryoSerializer(...)` 编译失败。

**原因：** Flink 2.2 把序列化器注册方法从 `ExecutionConfig` 移到了 `SerializerConfig`，且需要强转 `SerializerConfigImpl`。

**解法：**
```java
// Flink 1.x 写法（2.x 不可用）
env.getConfig().registerTypeWithKryoSerializer(clazz, serializer);

// Flink 2.2 写法
import org.apache.flink.api.common.serialization.SerializerConfigImpl;
((SerializerConfigImpl) env.getConfig().getSerializerConfig())
    .registerTypeWithKryoSerializer(clazz, serializer);
```

## 三、Flink 运行

### 3.1 ClassNotFoundException: SimpleUdfStreamOperatorFactory

**现象：** 用 `mvn exec:java` 运行 CDC 作业时报 `ClassNotFoundException`。

**原因：** Flink CDC 的 `PipelineExecutor` 依赖 SPI（Service Provider Interface）机制加载实现类。`mvn exec:java` 的类加载器隔离导致 SPI 找不到实现类。

**解法：** 用 `java -cp` 把所有依赖放在同一个 classpath 下运行。

```bash
# 构建 classpath
mvn dependency:build-classpath -pl flink-jobs -Dmdep.outputFile=/tmp/cp.txt -q
CP="flink-jobs/target/classes:$(cat /tmp/cp.txt)"

# 运行
java -cp "$CP" com.pipeline.flink.cdc.PostgresCdcToKafka
```

**教训：** Flink CDC / Table API 作业不要用 `mvn exec:java`，必须用 `java -cp`。

---

### 3.2 InaccessibleObjectException: java.nio.ByteBuffer

**现象：** 运行时报 `InaccessibleObjectException: Unable to make field ... java.nio.ByteBuffer.hb accessible`。

**原因：** Java 17 对 `java.nio`、`java.lang`、`java.util` 等模块做了强封装（JEP 403），Flink/Iceberg 内部需要反射访问 `ByteBuffer.hb` 等字段。

**解法：** 启动时加 `--add-opens` 参数：

```bash
java --add-opens java.base/java.nio=ALL-UNNAMED \
     --add-opens java.base/java.lang=ALL-UNNAMED \
     --add-opens java.base/java.util=ALL-UNNAMED \
     --add-opens java.base/sun.nio.ch=ALL-UNNAMED \
     -cp "$CP" ...
```

---

### 3.3 DataStream `.print()` 不输出

**现象：** 在 DWD 作业中用 `stream.print()` 调试，但控制台看不到输出。

**原因：** 作业用 `tableEnv.executeSql("INSERT INTO ...")` 提交，这只执行 Table API 的作业图。DataStream 的 `.print()` sink 不在 Table API 作业图中，不会被执行。

**解法：** 用 SLF4J 日志替代 `.print()`，或在 `tableEnv.executeSql()` 之前调用 `env.execute()` 执行 DataStream 部分（但这会导致作业分裂，不推荐）。

```java
// 推荐：用 LOG 调试
LOG.info("收到订单: {}", order.getOrder_id());
```

---

### 3.4 PG `too many clients` 连接耗尽

**现象：** AsyncIO 查询维表时报 `FATAL: too many connections for role`。

**原因：** Flink 高并行度 + HikariCP 默认 `maximumPoolSize=10`，导致总连接数超过 PG `max_connections`。

**解法：** 调小 HikariCP 连接池大小（本项目设为 3）：

```java
config.setMaximumPoolSize(3);
```

**教训：** AsyncIO 并发数 × 连接池大小 × 并行度 不能超过数据库最大连接数。

## 四、日志配置

### 4.1 log4j2.properties 是僵尸文件

**现象：** resources 下同时有 `log4j.properties` 和 `log4j2.properties`，改 `log4j2.properties` 的日志级别不生效。

**原因：** 项目实际用 **reload4j**（Log4j 1.x 继任者），只认 `log4j.properties`（1.x 格式）。`log4j2.properties`（2.x 格式）永远不会被加载。

**解法：** 删除 `log4j2.properties`，只保留 `log4j.properties`。

**如何判断用哪个日志框架：** 看依赖树的 SLF4J 绑定。
```bash
mvn dependency:tree -pl flink-jobs | grep slf4j
# slf4j-reload4j → 用 log4j.properties
# log4j-slf4j2-impl → 用 log4j2.properties/xml
```

---

### 4.2 data-generator 缺 slf4j-api 依赖

**现象：** 运行数据生成器报 `NoClassDefFoundError: org/slf4j/LoggerFactory`。

**原因：** `data-generator/pom.xml` 只引了 `log4j-slf4j2-impl`（SLF4J 到 Log4j2 的桥接），但 `slf4j-api` 本身没传递进来。

**解法：** 显式添加 `slf4j-api` 和 `log4j-core` 依赖：

```xml
<dependency>
    <groupId>org.slf4j</groupId>
    <artifactId>slf4j-api</artifactId>
    <version>${slf4j.version}</version>
</dependency>
<dependency>
    <groupId>org.apache.logging.log4j</groupId>
    <artifactId>log4j-core</artifactId>
    <version>${log4j2.version}</version>
</dependency>
```

## 五、环境配置

### 5.1 .env.example 端口与 docker-compose 映射不一致

**现象：** `.env.example` 写 `POSTGRES_PORT=5432`，但 `docker-compose.yml` 映射是 `5433:5432`（宿主机 5433 → 容器 5432）。照抄 `.env.example` 会连接失败。

**解法：** `.env.example` 改为 `POSTGRES_PORT=5433`，与 docker-compose 映射对齐。

**教训：** 环境变量模板必须与实际部署配置完全一致。

## 六、排查方法论

### 数据链路分段定位

当 Iceberg 无数据时，按链路逐段排查：

```
PG 有数据? → Kafka 有消息? → 反序列化成功? → JOIN 有输出? → Iceberg 有文件?
   ↓            ↓               ↓                ↓               ↓
 psql       kafka-console    DLQ topic        LOG 日志        ls data/*.parquet
```

| 段 | 验证命令 |
|----|---------|
| PG | `docker exec pg-cdc psql -U postgres -d ecommerce -c "SELECT count(*) FROM public.orders"` |
| Kafka | `kafka-console-consumer.sh --topic cdc.orders --from-beginning --max-messages 1` |
| 反序列化 | 检查 `dlq.cdc` topic 是否有大量消息 |
| JOIN | 检查 DWD 日志中是否有输出 |
| Iceberg | `ls warehouse/dwd/order_payment_wide/data/*.parquet` |

### 关键日志关键词

| 问题 | 搜索关键词 |
|------|-----------|
| Checkpoint 失败 | `Checkpoint.*failed`、`KryoException` |
| 反序列化失败 | `dlq`、`deserialize` |
| 维表查询失败 | `AsyncIO`、`HikariPool` |
| 作业启动失败 | `Exception`、`Caused by` |
