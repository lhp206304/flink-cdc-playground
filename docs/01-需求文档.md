# 生产级 Flink CDC 3.x 实时数据同步项目 — 需求文档

> 本文档为独立完整的需求说明，不依赖任何现有项目上下文，可直接用于新项目规划。
> 架构方案：**方案 B — CDC → Kafka → 统一处理 → Iceberg**
> 维表关联：**Broadcast 广播流（小维表）+ AsyncIO + JDBC（中维表）**

---

## 1. 项目概述

| 项 | 说明 |
|----|------|
| 项目名称 | 实时数据湖同步平台（CDC + Kafka 中转架构） |
| 项目定位 | 一套**贴近生产**的实时数据集成练习项目，掌握后可直接迁移到真实生产环境 |
| 核心架构 | Postgres CDC → Kafka（数据中转）→ Flink 统一处理 → Iceberg 数据湖 |
| 设计原则 | 配置外置、Kafka 扇出、链路解耦、语义精确、可观测、可恢复 |

---

## 2. 项目目标

1. 用 **Flink CDC 3.x Pipeline API（YAML）** 实现 Postgres → Kafka 的**整库实时同步**
2. 用 **Flink DataStream API（Java）** 消费 Kafka 中的 CDC 数据 + 业务事件流，做**实时 JOIN / 清洗 / 分流**，写入 Iceberg
3. Kafka 作为**中央数据总线**，CDC 数据可被多个下游共享
4. 引入**维表关联**：用 Broadcast 广播流关联小维表，用 AsyncIO + JDBC 关联中维表
5. 全部采用**生产级配置和最佳实践**（精确一次、Schema 演化、容错恢复、监控告警）
6. 让开发者通过本项目练习后，能独立上手真实生产环境的 CDC 同步任务

## 5. 数据源需求

### 5.1 PostgreSQL CDC 源

| 项 | 要求 |
|----|------|
| 同步方式 | 基于 WAL 逻辑复制（pgoutput 插件） |
| 同步范围 | 指定数据库下的多张表（支持正则匹配表名） |
| 同步模式 | 全量快照 + 增量 WAL（一体化，自动切换） |
| 同步对象 | 事务表：orders、order_items、payments（users、products 移至 dim 维表，不走 CDC） |
| 初始快照 | 作业首次启动时执行全量快照，之后进入增量模式 |
| DDL 同步 | 支持 Schema 演化（加列、改类型、加表自动同步到 Kafka） |
| **输出目标** | **Kafka（按表名自动路由到不同 Topic）** |

#### PostgreSQL 前置配置要求

```ini
# postgresql.conf
wal_level = logical              # 必须，开启逻辑复制
max_replication_slots = 4        # 复制槽数量上限
max_wal_senders = 4              # WAL 发送进程数上限
```

```sql
-- 每张同步表必须设置，否则 UPDATE/DELETE 拿不到变更前镜像
ALTER TABLE orders REPLICA IDENTITY FULL;
ALTER TABLE order_items REPLICA IDENTITY FULL;
ALTER TABLE payments REPLICA IDENTITY FULL;

-- CDC 账号需要 replication 属性
CREATE ROLE cdc_user WITH REPLICATION LOGIN PASSWORD 'cdc_pass';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO cdc_user;
```

### 5.2 Kafka 业务事件源

| 项 | 说明 |
|----|------|
| 数据类型 | 业务事件流（非 CDC 数据），如用户点击、价格变更 |
| Topic | 多个 Topic，每个 Topic 对应一类事件 |
| 数据格式 | JSON |
| 生产方 | 业务系统直接写入 Kafka（本项目用数据生成器模拟） |

> **注意**：Kafka 事件源只包含**CDC 里没有的行为信号**（点击、价格变更）。
> 订单数据走 CDC（cdc.orders），不发 events.orders，避免同实体数据重复。
> 维表数据（users、products）直接查 PostgreSQL 的 dim schema，不走 CDC 也不走 Kafka 事件。

### 5.3 维表数据源

| 维表 | 存储位置 | 关联方式 | 说明 |
|------|---------|---------|------|
| `dim_region`（地区编码） | PostgreSQL（dim schema） | **Broadcast 广播流** | 小维表（< 1000 行），全量加载到内存 |
| `dim_user`（用户信息+画像） | PostgreSQL（dim schema） | **AsyncIO + JDBC** | 中维表（万级行），异步并发查询；用户数据只存一份 |
| `dim_product`（商品信息） | PostgreSQL（dim schema） | **AsyncIO + JDBC** | 中维表，商品数据只存一份；价格由业务系统直接更新 |

> 维表数据由离线任务（或初始化脚本）写入 PostgreSQL 的 `dim` schema。
> 与事务表（`public` schema）同实例但 schema 隔离。
> **users、products 已从 public schema 移至 dim schema**，避免与 CDC 数据重复。
> 维表的更新由业务系统直接操作 PG，Flink 只负责读取。

### 5.4 数据生成器

本项目包含两个独立的数据生成器，分别为两条链路提供上游数据：

| 生成器 | 数据流向 | 目的 |
|--------|---------|------|
| Kafka 事件生成器 | 业务事件 → Kafka topic | 模拟业务系统事件流（链路 2 上游） |
| PostgreSQL 数据生成器 | 业务数据 → PG 表 → CDC → Kafka | 模拟数据库变更（链路 1 上游） |

两个生成器**独立运行**，通过环境变量配置速率，互不影响。

#### 5.4.1 Kafka 事件生成器

| 项 | 说明 |
|----|------|
| 写入目标 | Kafka topic（`events.clicks` / `events.product_price`） |
| 数据格式 | JSON |
| 速率控制 | 按 topic 配置速率，如 `clicks:70,product_price:30` |
| 事件类型 | 点击事件、商品价格变更事件 |
| 高级特性 | 重复主键、迟到事件、Schema 演化、热点 region |

> Kafka 生成器**只发 CDC 里没有的行为信号**（点击、价格变更）。
> 订单数据走 CDC，不发订单事件；维表数据直接查 PG dim schema。

#### 5.4.2 PostgreSQL 数据生成器（新增）

| 项 | 说明 |
|----|------|
| 写入目标 | PostgreSQL 业务表（public schema） |
| 写入方式 | JDBC Batch + HikariCP 连接池 |
| 速率控制 | 每秒事务数（TPS），可配置 |
| 操作类型 | INSERT / UPDATE / DELETE（比例可配置） |

**生成策略（按表）：**

| 表 | 生成策略 | 说明 |
|----|---------|------|
| orders | **高频 INSERT**（主流量） | 订单主表 |
| order_items | 随 orders 一起 INSERT | 订单明细 |
| payments | 随 orders 延迟 INSERT | 模拟支付延迟 |

> 维表（dim.dim_user、dim.dim_product）由初始化脚本灌入，生成器不写维表。
> 维表的更新由业务系统直接操作 PG。

**操作混合比例（默认）：**

| 操作 | 默认比例 | 可调 |
|------|---------|------|
| INSERT | 70% | ✅ |
| UPDATE | 20% | ✅ |
| DELETE | 10% | ✅ |

**高频写入优化：**

| 优化项 | 做法 |
|--------|------|
| JDBC Batch | 每批 500~1000 条，减少网络往返 |
| HikariCP 连接池 | 最大 10 连接，复用连接 |
| rewriteBatchedStatements | JDBC URL 参数，真正批量执行 |
| 多线程写入 | 每表独立写入线程，并发写入 |

**Kafka 生成器：**

```

## 6. 数据处理需求

### 6.1 链路 1：CDC 同步（Postgres → Kafka）

| 需求项 | 说明 |
|--------|------|
| 实现方式 | **Flink CDC Pipeline API（YAML 声明式）** |
| 同步范围 | 多表同步（正则匹配表名） |
| Topic 路由 | 按表名自动路由，如 `orders` → `cdc.orders` |
| 数据格式 | Debezium JSON（含 before/after/op/source 元信息） |
| Schema 演化 | 源表加列/改类型时，自动同步到 Kafka 消息 |
| 事务语义 | Exactly-Once（依赖 Kafka 事务 + Flink Checkpoint） |

> **YAML 示例（sink 为 kafka）：**
> ```yaml
> source:
>   type: postgres-cdc
>   hostname: ${POSTGRES_HOST}
>   port: ${POSTGRES_PORT}
>   username: ${POSTGRES_CDC_USER}
>   password: ${POSTGRES_CDC_PASSWORD}
>   database-name: ecommerce
>   table-name: public\.(orders|order_items|payments)
>   slot.name: flink_cdc_slot
>   plugin.name: pgoutput
>
> sink:
>   type: kafka
>   properties.bootstrap.servers: ${KAFKA_BOOTSTRAP_SERVERS}
>   topic: cdc.*
> ```

### 6.2 链路 2：统一处理（Kafka → Iceberg）

| 需求项 | 说明 |
|--------|------|
| 实现方式 | **Flink DataStream API（Java 编程式）** |
| 消费源 | Kafka 中所有 CDC Topic + 业务事件 Topic |
| 数据清洗 | 过滤脏数据、空值校验、格式标准化 |
| 字段转换 | 时间格式统一、枚举值映射、类型转换、DECIMAL 解析 |
| 实时 JOIN | 订单 CDC 数据 + 支付事件流按 order_id 关联 |
| 维表关联 | 见 6.3 |
| 侧输出 | 脏数据 / 解析失败数据 → 死信侧输出流 |
| 分流写入 | 不同业务表写入 Iceberg 不同层（ODS / DWD） |
| 写入模式 | ODS 层 upsert（按主键），DWD 层 append |

### 6.3 维表关联（核心新增需求）

#### 6.3.1 Broadcast 广播流 — 小维表（dim_region）

| 项 | 说明 |
|----|------|
| 维表 | `dim_region`（地区编码表，< 1000 行） |
| 加载方式 | 维表数据通过定时从 PostgreSQL 加载，以广播流形式分发到所有 TaskManager |
| 存储位置 | 每个 TaskManager 内存中的 BroadcastState（Map<region_id, Region>） |
| 关联方式 | 流数据到达时，从 BroadcastState 中按 region_id 查找 |
| 刷新策略 | 定时全量加载替换 BroadcastState |
| 优点 | 关联速度极快（内存查 Map），不压数据库 |

```
维表更新 → 定时查询 PG → 广播流 → BroadcastState
事实流 ─────────────────────────────────────┘
                                              │ 内存查 Map
                                              ▼
                                        富化后的流数据
```

#### 6.3.2 AsyncIO + JDBC — 中维表（dim_user）

| 项 | 说明 |
|----|------|
| 维表 | `dim_user`（用户画像表，万级行） |
| 加载方式 | 每条流数据到达时，通过 AsyncDataStream 异步并发查询 PostgreSQL |
| 存储位置 | PostgreSQL（dim schema，不加载到内存） |
| 关联方式 | `AsyncDataStream.unorderedWait` 并发查询，查回用户画像后填充 |
| 并发度 | 100（可配置） |
| 超时 | 5 秒（可配置），超时返回 null 不关联 |
| 优点 | 支持大维表，吞吐高，维表实时更新可见 |

```
事实流 → AsyncDataStream.unorderedWait → 并发查 PostgreSQL(dim.dim_user) → 富化后的流数据
         (并发度 100, 超时 5s)
```

### 6.4 共用能力

| 能力 | 说明 |
|------|------|
| Checkpoint | **3 秒间隔**，RocksDB 增量 Checkpoint，精确一次语义（见下方详细配置） |
| 状态恢复 | 支持从 Checkpoint / Savepoint 恢复 |
| 重启策略 | 固定延迟重启，最多 3 次，间隔 10 秒 |
| 配置外置 | 所有连接信息走环境变量，无硬编码、无回退默认值 |
| 脏数据处理 | 解析失败的数据写入侧输出，不中断主流程 |
| 配置快照 | 作业启动时输出最终生效配置快照 |

#### Checkpoint 详细配置（满足 Kafka → Iceberg < 5 秒延迟）

> **关键原理**：Iceberg Sink 采用两阶段提交，数据只有在 Checkpoint 完成时才提交到 Iceberg 表并对外可见。因此 **Iceberg 数据可见延迟 ≈ Checkpoint 间隔**。要满足 < 5 秒可见延迟，Checkpoint 间隔必须设为 5 秒以内。

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `execution.checkpointing.interval` | **3s** | Checkpoint 间隔，决定 Iceberg 数据可见延迟 |
| `execution.checkpointing.min-pause` | 1s | 两次 Checkpoint 之间最小间隔，防止重叠 |
| `execution.checkpointing.timeout` | 60s | 单次 Checkpoint 超时时间 |
| `execution.checkpointing.tolerable-failed-checkpoints` | 3 | 允许连续失败的 Checkpoint 次数 |
| `state.backend` | rocksdb | 增量 Checkpoint，减少状态快照数据量 |
| `state.backend.incremental` | true | 启用增量 Checkpoint |

> **小文件问题**：Checkpoint 间隔小（3s）会导致 Iceberg 产生大量小文件，需配合 Compaction 作业定期合并（见 F-13）。

## 7. Kafka 设计

### 7.1 Topic 规划

| Topic 命名 | 数据来源 | 说明 |
|------------|---------|------|

| `transaction.state.log.replication.factor` | 1 | 单机环境 |

## 9. 维表设计

### 9.1 dim_region（小维表，Broadcast）

| 字段 | 类型 | 说明 |
|------|------|------|

## 11. 非功能需求

| 维度 | 要求 |
|------|------|
| 语义保证 | 端到端 Exactly-Once（CDC→Kafka→Iceberg 全程不丢不重） |
| 延迟 | CDC 同步到 Kafka < 3 秒；Kafka 到 Iceberg < 5 秒 |
| 容错 | 作业失败自动重启，从 Checkpoint 恢复 |
| 可维护性 | CDC 任务用 YAML 配置，改配置不重编译 |
| 可观测性 | 作业启动时输出最终生效配置快照 |
| 可移植性 | 本地 Docker Compose 一键启动，生产只需改环境变量 |
| 可扩展性 | CDC 新增表只需改 YAML 正则，无需改代码 |

#### 延迟指标实现说明

| 链路 | 延迟要求 | 实现方式 |
|------|---------|---------|
| CDC → Kafka | < 3 秒 | Kafka 每条写入立即可见，延迟取决于网络和处理速度，天然满足 |
| Kafka → Iceberg | < 5 秒 | Iceberg 数据在 Checkpoint 完成后才提交可见，因此 Checkpoint 间隔设为 **3 秒**（见 6.4 节） |

ICEBERG_CATALOG_NAME=local_catalog

```
